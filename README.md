# 台风实况预警平台

面向沿海居民的台风实况信息与分级预警网站。

## 项目计划书

### 1. 项目概述

本项目建设一个移动端优先、信息清晰、适合应急场景使用的台风实况网站。用户无需具备气象专业知识，即可快速知道：当前影响自己的台风叫什么、位于哪里、正在往哪里走、风力有多大，以及自己所在地区是否需要采取行动。

平台的核心原则是：信息来源可靠、更新时间明确、风险表达直白、关键内容在弱网和小屏幕上也能读清楚。

### 2. 目标用户与使用场景

- 沿海居民：查看当前位置附近是否受台风影响、何时需要避险。
- 渔民、海上作业人员和港口从业者：关注风力、移动方向、登陆可能性和更新时间。
- 社区与基层应急人员：快速查看辖区风险、转发预警信息。
- 家庭成员：为老人、儿童或不在身边的家人确认安全提醒。

典型场景包括：台风生成后查看动态、风圈接近时判断是否需要撤离、登陆前后确认风雨影响、预警解除后查看最新路径和恢复提示。

### 3. 产品目标

#### 首期目标（MVP）

1. 展示当前活跃台风及其基本状态。
2. 清晰呈现台风名称、当前位置、移动方向、移动速度、最大风力和中心气压。
3. 在地图上展示历史路径、未来预测路径、影响范围和更新时间。
4. 依据官方预警信息展示分级预警，并解释居民应采取的行动。
5. 支持用户选择城市或使用定位，查看本地风险摘要。
6. 在手机端优先保证首页在几秒内读懂，关键数据不依赖复杂图表。

#### 后续目标

- 增加降雨、风暴潮、海浪和高温等伴随灾害信息。
- 支持订阅指定城市、台风或预警等级的通知。
- 提供无障碍模式、家人共享和社区应急入口。
- 支持多语言和面向游客的简明版安全提示。

### 4. 首页信息架构

首页按“先判断风险、再查看细节”的顺序组织：

1. **顶部状态栏**：数据更新时间、数据来源、当前定位城市。
2. **风险摘要卡**：本地当前预警等级、是否建议减少外出、下一次更新时间。
3. **台风概览卡**：台风名称、编号、当前等级、当前位置、移动方向与速度。
4. **关键指标**：最大风力、阵风、中心气压、七级/十级风圈半径等。
5. **路径地图**：历史实况路径、未来预测路径、预测时间点、当前位置标记。
6. **预警与行动建议**：用普通语言说明“现在该做什么”。
7. **详细信息与来源**：预报机构、发布时间、数据说明、免责声明。

### 5. 台风核心字段

每个台风对象至少包含以下字段：

- 台风名称、国际编号、本地编号（如有）。
- 当前中心位置：纬度、经度、所在海域或最近城市。
- 移动方向、移动速度、更新时间。
- 最大持续风速、最大阵风、风力等级、中心气压。
- 历史观测点：时间、位置、风速、气压。
- 未来预测点：预计时间、位置、风速、强度和预测误差范围。
- 风圈半径：七级风圈、十级风圈、十二级风圈（以数据源实际提供为准）。
- 当前影响区域及关联预警。

### 6. 分级预警设计

平台应优先展示气象部门或应急部门发布的官方预警原文与等级，不自行替代官方灾害预警。产品层可将风险翻译成居民易懂的行动等级：

| 平台等级 | 颜色建议 | 居民看到的含义 | 页面行动提示 |
| --- | --- | --- | --- |
| 关注 | 蓝色 | 台风已生成或可能影响本区域 | 关注后续路径，准备应急物资 |
| 防范 | 黄色 | 预计将带来明显风雨影响 | 减少非必要出行，检查门窗和排水 |
| 避险 | 橙色 | 风雨或风暴潮风险较高 | 避开海边、河道和危险建筑，按通知转移 |
| 紧急 | 红色 | 可能造成严重灾害或正在发生 | 立即遵循当地政府指令，进入安全场所 |

实现要求：

- 等级、发布时间、发布机构、影响区域必须同时显示。
- 颜色不能作为唯一提示，必须配合文字、图标和行动建议。
- 红色或橙色预警在首页首屏突出，并支持语音/无障碍朗读预留。
- 当官方预警与平台计算风险不一致时，优先显示官方预警，并标注差异来源。
- 预警卡提供“为什么收到”和“我现在该做什么”，减少用户误解。

### 7. 数据与技术方案

#### 数据来源原则

- 首选中国气象局、国家预警信息发布平台、地方气象台和应急管理部门等官方或授权数据源。
- 所有数据记录发布时间、更新时间、来源机构和数据版本。
- 对实时接口设置超时、重试、缓存和“数据可能延迟”提示。
- 预报路径必须明确是预测，不应使用与实况相同的视觉样式。

#### 建议架构

- 前端：响应式 Web，移动端优先；地图使用成熟地图 SDK 或开源地图方案。
- 后端：提供台风、路径点、预警、区域风险和数据源状态 API。
- 数据层：保存当前快照与历史记录，便于展示路径回放和追溯。
- 任务调度：按数据源频率拉取、校验、标准化并发布最新数据。
- 监控：监测接口延迟、数据中断、异常坐标、预警更新失败和地图服务不可用。

建议的核心接口：

```text
GET /api/typhoons/active
GET /api/typhoons/{id}
GET /api/typhoons/{id}/track
GET /api/alerts?region={regionCode}
GET /api/risk-summary?lat={lat}&lng={lng}
GET /api/data-status
```

### 8. 关键交互与可用性要求

- 默认先展示用户所在城市；未授权定位时提供城市搜索。
- 所有关键数据同时显示“值 + 单位 + 更新时间”。
- 地图提供列表模式，避免用户无法理解地图或网络较慢时无法获取信息。
- 支持一键复制/分享风险摘要，分享内容包含来源和时间。
- 弱网下优先加载预警等级、台风名称、位置、方向和风力；地图可延后加载。
- 文字对比度、字号、按钮尺寸满足移动端无障碍要求。
- 不使用“安全”“不会登陆”等绝对化表述，避免造成错误安全感。

### 9. 实施阶段

#### 阶段一：需求与数据验证（1 周）

- 确定首批服务区域和官方数据源。
- 梳理预警等级、字段定义、更新时间和异常处理规则。
- 制作低保真页面流程并邀请沿海居民评审。

#### 阶段二：MVP 开发（2–3 周）

- 完成台风数据接入、标准化和缓存。
- 完成首页、台风详情页、地图路径、预警卡和城市选择。
- 加入数据更新时间、来源和接口异常提示。

#### 阶段三：测试与试运行（1–2 周）

- 用历史台风数据回放验证路径、风力和预警展示。
- 做移动端、弱网、接口中断、定位拒绝和高并发测试。
- 邀请社区工作人员或沿海居民进行可用性测试。

#### 阶段四：上线与迭代（持续）

- 建立数据质量巡检和应急联系人机制。
- 复盘用户查询、分享和预警点击行为。
- 增加通知订阅、风暴潮、降雨和无障碍能力。

### 10. 验收标准

- 用户在首页 10 秒内能找到台风名称、位置、方向和风力。
- 预警等级、颜色、文字含义、发布时间和来源同时可见。
- 历史路径与预测路径视觉区分明显，时间点和单位完整。
- 数据源中断时，页面不展示过期数据为“实时数据”，并明确提示更新时间。
- 在常见手机宽度下无横向滚动，关键操作可单手完成。
- 使用历史数据回放时，页面展示结果与输入数据一致。
- 所有对外安全提示均经过气象/应急专业人员审核。

### 11. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 官方接口不稳定或限流 | 无法及时更新 | 多源冗余、缓存、状态监控、明确延迟提示 |
| 不同机构字段和等级不一致 | 用户误解 | 建立标准化映射，保留原始来源和原文 |
| 预测路径存在不确定性 | 错误决策 | 展示预测时间、误差范围和“预测非实况”说明 |
| 极端天气访问量激增 | 页面不可用 | CDN、缓存、静态降级页、压测和限流 |
| 颜色或术语理解错误 | 延误避险 | 颜色+文字+行动建议，多轮用户测试 |

### 12. 首批待确认事项

1. 首期覆盖哪些省市或海域。
2. 采用哪些官方数据源及授权方式。
3. 是否需要短信、微信服务号或浏览器通知。
4. 是否需要后台管理台来维护应急提示和数据源状态。
5. 网站是否需要备案、域名、隐私政策和定位授权说明。
